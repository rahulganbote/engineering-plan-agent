## Pattern Selection
pattern: Workflow-centric service with external verification adapters
pattern_justification: |
  Onboarding is a stateful workflow with external vendor waits and analyst reviews; a simple CRUD app was rejected because it would not handle retries, SLAs, or evidence capture cleanly. Team size is assumed to be 5-8 engineers, which is enough for clear component ownership without creating unnecessary platform overhead. The primary NFR driver is Seller dashboard actions respond in <= 2 seconds P95. The architecture respects compliance constraints for KYC/KYB, sanctions screening, marketplace product policy, SOC 2.

## Components
components:
  - name: Seller Workflow API
    responsibility: Manages application state and dashboard actions.
    technology: Java Spring Boot + Camunda
    interfaces: [REST, BPMN jobs]
  - name: Verification Adapter
    responsibility: Orchestrates KYC, tax, sanctions, and bank checks.
    technology: TypeScript Node.js
    interfaces: [REST, webhooks]
  - name: Catalog Readiness Service
    responsibility: Validates listing attributes and restricted categories.
    technology: Python FastAPI
    interfaces: [REST, rules files]
  - name: Evidence Store
    responsibility: Stores documents, decisions, and policy versions.
    technology: PostgreSQL + S3
    interfaces: [SQL, object API]

## Data Flow
data_flow:
  - "1. User or upstream system submits data for Marketplace Seller Onboarding and Compliance."
  - "2. Entry service validates identity, schema, and consent or policy constraints."
  - "3. Processing components enrich, score, or route the request using Seller profiles, business documents, tax IDs, bank verification status, catalog submissions, review decisions."
  - "4. Workflow/API layer presents results to Marketplace sellers, compliance analysts, category managers and records audit evidence."
  - "5. Failure path: integration failures are queued, retried, and shown with actionable status."
