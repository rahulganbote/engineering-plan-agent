## Pattern Selection
pattern: Event-driven microservices
pattern_justification: |
  High-volume banking events and strict alert latency favor event-driven processing; a modular monolith was rejected because fraud scoring, notification, and case routing scale independently. Team size is assumed to be 5-8 engineers, which is enough for clear component ownership without creating unnecessary platform overhead. The primary NFR driver is P95 risk decision latency <= 700 ms for 150 events per second. The architecture respects compliance constraints for FFIEC, GLBA, SOC 2, internal model-risk review.

## Components
components:
  - name: Event Gateway
    responsibility: Validates and normalizes banking events.
    technology: AWS MSK + Kafka Schema Registry
    interfaces: [Kafka topics, REST admin API]
  - name: Risk Scoring Service
    responsibility: Computes risk scores and explanations for payment activity.
    technology: Python FastAPI + XGBoost model
    interfaces: [REST, Redis feature cache]
  - name: Notification Orchestrator
    responsibility: Routes push, SMS, and secure-inbox alerts.
    technology: TypeScript Node.js on ECS
    interfaces: [REST, SNS, vendor SMS API]
  - name: Analyst Case API
    responsibility: Stores dispositions and exposes case details.
    technology: Java Spring Boot + PostgreSQL
    interfaces: [REST, JDBC]

## Data Flow
data_flow:
  - "1. User or upstream system submits data for Real-Time Digital Banking Fraud Alerts."
  - "2. Entry service validates identity, schema, and consent or policy constraints."
  - "3. Processing components enrich, score, or route the request using Digital session events, transfer metadata, device intelligence, customer contact preferences, analyst dispositions."
  - "4. Workflow/API layer presents results to Retail banking customers, fraud analysts, contact-center agents and records audit evidence."
  - "5. Failure path: integration failures are queued, retried, and shown with actionable status."
