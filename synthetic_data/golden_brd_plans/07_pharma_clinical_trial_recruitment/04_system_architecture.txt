## Pattern Selection
pattern: RAG-assisted rules engine with batch cohort processing
pattern_justification: |
  Clinical criteria benefit from RAG extraction but final matching must be deterministic and auditable; pure LLM matching was rejected due to GxP and explainability constraints. Team size is assumed to be 5-8 engineers, which is enough for clear component ownership without creating unnecessary platform overhead. The primary NFR driver is Refresh candidate lists for a trial with 100,000 patients in <= 2 hours. The architecture respects compliance constraints for HIPAA, GxP validation expectations, 21 CFR Part 11, IRB recruitment rules.

## Components
components:
  - name: Protocol Ingestion
    responsibility: Extracts and versions trial criteria for review.
    technology: Python + LangChain + OpenAI
    interfaces: [REST, document parser]
  - name: Eligibility Rules Engine
    responsibility: Runs approved inclusion and exclusion rules.
    technology: Python + durable rules
    interfaces: [Batch jobs, SQL]
  - name: FHIR Data Mart
    responsibility: Stores normalized patient facts for cohort queries.
    technology: PostgreSQL + OMOP mapping
    interfaces: [SQL, FHIR ingest]
  - name: Coordinator Worklist
    responsibility: Displays candidates, rationale, and outreach status.
    technology: React + FastAPI
    interfaces: [REST]

## Data Flow
data_flow:
  - "1. User or upstream system submits data for Clinical Trial Recruitment Matching Platform."
  - "2. Entry service validates identity, schema, and consent or policy constraints."
  - "3. Processing components enrich, score, or route the request using FHIR Conditions, Observations, Medications, demographics, consent status, protocol eligibility criteria."
  - "4. Workflow/API layer presents results to Clinical research coordinators, investigators, patient navigators and records audit evidence."
  - "5. Failure path: integration failures are queued, retried, and shown with actionable status."
