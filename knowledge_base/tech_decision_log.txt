## Approved Technology Stack (Current Org Standards)

### Languages
- Python 3.11+: Data pipelines, ML services, scripting, backend APIs (FastAPI)
- TypeScript/Node.js: Frontend (React/Next.js), BFF services, real-time APIs
- Java 17: High-throughput transaction processing, legacy system integration
- Go: Network-intensive services, CLI tools, infrastructure tooling

### Databases — Relational
- PostgreSQL 15: Default relational DB for new services — ACID compliance, strong ecosystem
- MySQL: Legacy only — no new services approved on MySQL as of 2023
- Oracle: System of record for Finance/ERP — migration planned 2025

### Databases — Non-relational
- Redis: Session storage, caching, rate limiting, pub/sub for low-latency use cases
- MongoDB: Document storage for unstructured content (CMS, user preferences)
- DynamoDB: Serverless event stores, audit logs requiring infinite scale

### Message Queues / Streaming
- Apache Kafka: High-throughput event streaming (>10,000 messages/sec)
- AWS SQS/SNS: Standard async messaging, fan-out notifications
- RabbitMQ: Legacy only — no new services after 2022

### Infrastructure
- AWS: Primary cloud provider (enterprise agreement, 30% volume discount)
- Kubernetes on EKS: Container orchestration for all production services
- Terraform: Infrastructure as code — mandatory for all production environments
- GitHub Actions: CI/CD standard — Jenkins decommissioned Q4 2024

### Observability Stack
- Datadog: APM, infrastructure monitoring, log aggregation (primary)
- PagerDuty: On-call alerting and incident management
- Grafana: Internal dashboards pulling from Prometheus for custom metrics

### Security
- HashiCorp Vault: Secrets management — no hardcoded credentials permitted
- AWS IAM with least-privilege: All services use IAM roles, no long-lived keys
- Snyk: Dependency vulnerability scanning in all CI pipelines

### DL-2024-031 — Vector Database Selection
Date: 2024-09-15
Context: Three teams evaluating vector databases for RAG applications
Decision: Pinecone (serverless) for managed, Qdrant self-hosted for cost-sensitive
Rationale: Pinecone reduces ops overhead for teams without MLOps capacity.
  Qdrant chosen when team can manage infrastructure and cost is primary concern.
  ChromaDB rejected — not production-ready for > 1M vectors.
Outcome: Payments AI pilot on Pinecone — 99.97% uptime, P99 < 25ms query latency

### DL-2024-035 — Prompt Injection Detection Strategy
Date: 2024-11-01
Context: Three AI systems in production needed consistent injection defense
Decision: Two-layer detection — regex pre-filter (Layer 1) + LLM semantic scan using gpt-4o-mini (Layer 2)
Rationale: Regex alone misses obfuscated attacks (unicode tricks, character substitution).
  LLM alone is non-deterministic and costly. Two layers: regex catches known patterns at ~0ms;
  gpt-4o-mini catches novel/obfuscated at ~800ms only when regex passes.
  Fail-open on scanner error (regex already passed = acceptable risk vs blocking all uploads).
Outcome: Zero confirmed injection incidents across 3 production systems over 6-month observation period.

### DL-2024-033 — Pydantic v2 for Agent Output Contracts
Date: 2024-10-12
Context: Multi-agent pipelines needed runtime validation at every handoff to prevent hallucinated schema fields from propagating
Decision: Pydantic v2 with field_validator on all agent output models; citations field required (min_length=1)
Rationale: Pydantic v1 lacked performance at scale. v2 is 5-17× faster validation.
  Enforcing citations at schema level (not prompt level) guarantees grounding is structural.
  Prompts can be ignored by LLMs; schema validation cannot.
Outcome: Zero schema validation escapes in production; citations enforcement improved grounding scores by avg 0.8 points.

### DL-2024-029 — CI/CD Security Scanning Standard
Date: 2024-08-20
Context: 3 P1 incidents caused by known CVEs in unpinned dependencies
Decision: Snyk dependency scanning in CI pipeline; block on HIGH or CRITICAL CVEs; weekly scheduled scan
Rationale: Manual dependency review missed 2 of 3 incidents. Automated scanning at PR time
  catches issues before merge. Snyk chosen over OWASP Dependency-Check for GitHub integration quality.

### DL-2023-052 — Multi-Tenant Isolation Pattern (SaaS)
Date: 2023-12-05
Context: First B2B SaaS product required tenant data isolation; 3 isolation strategies evaluated
Decision: Per-tenant namespace in Kubernetes + per-tenant S3 bucket + per-tenant DB schema (not shared tables with tenant_id column)
Rationale: Shared-table isolation with tenant_id column has too many ways to fail (missing WHERE clause, ORM quirks).
  Per-namespace + per-bucket provides isolation at infrastructure level, not just application level.
  Defense-in-depth: attacker must bypass 3 independent isolation layers.
Outcome: External penetration test found zero cross-tenant access vulnerabilities. SOC 2 Type II achieved.

### DL-2023-041 — Event Sourcing for Audit Trails
Date: 2023-09-18
Context: Legal and financial products required immutable, court-admissible audit logs
Decision: Append-only event store with SHA-256 hash chain; PostgreSQL with write-only service account; no delete API at any layer
Rationale: Relational audit tables with DELETE permission are not court-admissible (records can be removed).
  Append-only with hash chain provides mathematical proof of record integrity.
  PostgreSQL with write-only IAM role enforces immutability at infrastructure level.
Outcome: Audit trail accepted as evidence in 2 legal proceedings. SOC 2 Type II compliance achieved.

### DL-2023-028 — gRPC for Internal Service Communication
Date: 2023-06-14
Context: 40+ microservices with REST APIs causing integration friction and performance issues
Decision: gRPC + Protobuf for all internal service-to-service communication; REST kept for external APIs
Rationale: gRPC provides: typed contracts (Protobuf), 40% lower latency than REST, HTTP/2 multiplexing,
  bi-directional streaming. External REST kept for partner compatibility.
  Code generation from Protobuf eliminates integration errors between teams.
Outcome: Internal API integration time reduced from 3 days to 4 hours average. P95 latency improved 38%.

### DL-2022-055 — Kubernetes Resource Limits Enforcement
Date: 2022-11-30
Context: Runaway container in shared cluster caused production outage for unrelated services
Decision: Mandatory CPU and memory limits on all Kubernetes pods; LimitRange enforced at namespace level
Rationale: Without limits, one misbehaving pod can exhaust node resources and cause eviction of healthy pods.
  LimitRange at namespace level prevents new deployments without limits (operator cannot forget).
  AI/LLM workloads particularly prone to memory exhaustion under unexpected load.
Outcome: Zero noisy-neighbor incidents since adoption. Memory-related pod crashes reduced by 94%.
